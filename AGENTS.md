## Code style

Avoid overusing comments in code. Prefer clear naming, simple structure, and self-explanatory code over comments that merely restate what the code does.

Add comments only when they provide information that is not obvious from the code itself, such as:

- explaining complex or non-obvious logic;
- documenting important assumptions, constraints, edge cases, or workarounds;
- explaining why a particular approach was chosen when the reason is not apparent;
- warning about behavior that could easily be misunderstood or accidentally broken.

Do not add comments for trivial operations, obvious control flow, variable assignments, function calls, or code whose intent is already clear from its names and structure.

Prefer comments that explain **why**, not **what**. If a comment can be removed by making the code clearer, improve the code instead.

## Commits

ALWAYS write commit messages in English. You MUST use the semantic commits format. NEVER use `src/localization/locales/*` files to write commit messages, except in the case where these are the only changes.

NEVER make push or pull requests without ASK an user!

**Never delete untracked files.** They may contain work-in-progress notes, scratch pads, or local context that is not recoverable from git. Always ask before removing any untracked file.

## Changelog

ALWAYS write changelog entries in Russian. You MUST use user-friendly language and keep sentence short and simple.

## Project Facts

- Bun is the package manager for installs, scripts, and standalone compilation; `bun.lock` is committed. The distributed CLI supports Node.js `>=22.19.0`.
- CLI entrypoint is `src/index.ts`; the published `bin` points at generated `dist/index.js`.
- Core execution is in `src/client.ts`: it builds concurrent `listr2` tasks over deduped positional URLs, uses `@vot.js/node`/`@vot.js/shared`, and writes either downloads or preview links.
- CLI options are defined in `src/resources/schema.ts`; help text is separate in `src/resources/messages.ts`, so option changes usually need both files updated.

## Generated Files

- `src/config.ts` is updated by `bun run update:config`: the script imports its existing config, sets the version from `package.json`, formats it, and writes it back.
- `src/types/schema.ts` is generated by `bun run update:schema` from `src/resources/schema.ts`; edit the schema source, then regenerate.
- `bun run build`, `bun run build:raw`, and `bun run compile` run `update:all`; `build:bun` aliases `build`.

## Commands

- Install deps: `bun install`.
- Regenerate config and schema only: `bun run update:all`.
- Build Node output in `dist/`: `bun run build` (or its `build:bun` alias). `build:raw` runs `tsc` followed by `tsc-esm-fix`.
- Cross-compile standalone binaries into `build/`: `bun run compile`.
- Lint: `bun run lint`; auto-fix: `bun run lint:fix`.
- Format check/write with oxfmt: `bun run fmt:check` / `bun run fmt`.
- There is no test script or CI runtime smoke test; verify changes with lint, format check, and the relevant build command.

## Tooling Quirks

- Pre-commit is Lefthook: oxfmt runs on changed files, and `bun run lint` runs on staged JS/TS files; both jobs can stage fixes.
- Formatting and linting use `.oxfmtrc.json` and `.oxlintrc.json`.
- `.gitignore` excludes `dist/`, `build/`, `node_modules/`, `debian/`, `*.mp3`, `*.tmp`, and other local/tool artifacts; avoid treating ignored build/media files as source.
- README notes Bun cross-compilation can fail on Windows with `Failed to move cross-compiled bun binary into cache directory`; use WSL or move the repo to the C: drive for that case.

## Release/CI

- Build CI installs with Bun and runs `bun build:bun`; compile CI runs `bun compile` on Ubuntu.
- Release workflow runs on pushes to `main` and creates a draft release from compiled artifacts. Its `tag_name` is currently `github.ref`; it does not select a version tag.
